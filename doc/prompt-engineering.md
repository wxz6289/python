# 提示工程（Prompt Engineering）核心内容与最佳实践

提示工程的本质不是“写一句神奇咒语”，而是把模型能力转化为**可控、可复现、可评估**的工程流程。

---

## 1. 什么是提示工程

提示工程是为大语言模型设计输入与交互策略的过程，目标是：

- 提高输出质量（准确性、完整性、可读性）；
- 降低不确定性（格式漂移、幻觉、跑题）；
- 降低成本（token 与延迟）；
- 提升可维护性（版本化、回归测试、可追踪）。

一个完整提示通常包含：

- **系统约束（System）**：角色、边界、行为规范；
- **任务指令（Instruction）**：要做什么、做到什么程度；
- **上下文（Context）**：背景、数据、业务规则；
- **输出规范（Output format）**：结构、字段、语气、长度；
- **示例（Few-shot）**：正反样例，校准风格和判定标准。

---

## 2. 提示设计的核心原则

## 2.1 明确目标（Goal-first）

- 先定义“成功输出是什么”，再写提示词。
- 把抽象目标改写为可检查标准，例如：
  - “总结一下” -> “输出 3 条要点，每条 <= 30 字，并附 1 条风险”。

## 2.2 指令具体、边界清晰

- 说清楚允许做什么、不允许做什么。
- 明确“信息不足时如何处理”，例如“无法确认时返回 `UNKNOWN` 并说明缺失字段”。

## 2.3 输出先行（Format-first）

- 在提示中先定义输出 schema，再要求模型生成。
- 生产场景优先 JSON/结构化输出，减少后处理脆弱性。

## 2.4 逐步分解（Decomposition）

- 复杂任务拆成子任务（分类 -> 检索 -> 生成 -> 校验）。
- 不要一次提示里混太多目标，降低冲突与漂移。

## 2.5 少而精的示例

- few-shot 示例优先“代表性覆盖”，而不是数量堆叠。
- 示例风格必须和目标输出一致，避免“示例污染”。

---

## 3. 常见提示模式

## 3.1 零样本（Zero-shot）

仅给指令和格式约束，不给示例。

适合：

- 任务简单、格式要求清晰；
- 对速度和成本敏感的场景。

## 3.2 少样本（Few-shot）

通过 2-5 个高质量示例校准行为。

适合：

- 分类边界模糊；
- 风格要求强（客服、法律、医疗摘要）；
- 需要稳定的结构化输出。

## 3.3 角色与语气控制

通过系统提示定义角色（如“资深 Python 代码审查员”）。

注意：

- 角色是“约束”，不是“人格表演”；
- 业务规则应明确写在指令中，而非只靠角色语气。

## 3.4 结构化输出

优先使用 JSON schema 或函数调用（tool/function calling）：

- 提升稳定性；
- 易于程序校验；
- 降低解析错误。

## 3.5 检索增强（RAG Prompting）

把检索结果作为受控上下文注入，要求模型“仅依据证据回答并引用来源”。

关键点：

- 上下文分块清晰，附来源 ID；
- 要求“若证据不足则拒答”；
- 输出时标注引用片段/文档 ID。

---

## 4. 提示模板建议（可直接套用）

```text
[System]
你是{role}。遵循以下规则：
1) 仅使用给定上下文，不要臆测；
2) 信息不足时返回 UNKNOWN；
3) 输出必须符合指定格式。

[Task]
请完成：{task}

[Context]
{context}

[Constraints]
- 语言：中文
- 长度：不超过{max_len}字
- 禁止输出：{forbidden}

[Output Format]
返回 JSON：
{
  "answer": "string",
  "confidence": "high|medium|low",
  "citations": ["doc_id:line_range"]
}
```

---

## 5. 与模型能力匹配（模型选择视角）

- 简单提取/分类：优先小模型，低成本高吞吐；
- 复杂推理/代码审查：选择推理更强模型；
- 长文档分析：优先长上下文模型，但仍需检索与压缩；
- 多模态任务：确认模型原生支持图像/音频输入。

提示工程不是万能补丁：当任务超出模型能力上限时，应调整流程或换模型。

---

## 6. 评测与迭代方法（最重要）

## 6.1 建立评测集（Eval Set）

- 按业务场景构建 20-200 条高价值样本；
- 覆盖正常样本、边界样本、对抗样本；
- 每条样本定义“期望输出”和评分规则。

## 6.2 指标体系

- **准确性**：事实正确、逻辑一致；
- **格式合规率**：是否满足 schema；
- **拒答正确率**：该拒答时是否拒答；
- **稳定性**：同输入多次输出波动；
- **成本/延迟**：token、响应时间。

## 6.3 版本化与回归

- 每次改提示词都要加版本号（如 `prompt_v7`）；
- 对比旧版本做 A/B 或离线回归；
- 上线后持续采集失败样本回灌评测集。

---

## 7. 生产环境最佳实践

1. **分层提示**：System（全局规则）+ Task（任务）+ Runtime Context（动态数据）。
2. **结构化优先**：能用 JSON 就不要自由文本。
3. **防注入设计**：把用户输入当不可信数据，不允许覆盖系统规则。
4. **上下文最小化**：只给必要信息，减少噪声与成本。
5. **失败可恢复**：解析失败重试；重试失败走降级模板。
6. **显式拒答策略**：证据不足时返回标准错误结构，不瞎编。
7. **日志可追踪**：记录模型、prompt 版本、输入摘要、输出、耗时、token。
8. **敏感信息治理**：提示词与日志中做脱敏，避免泄露 PII/密钥。

---

## 8. 常见误区与修正

- 误区：提示词越长越好  
  修正：只保留有效约束，冗余会稀释重点。

- 误区：只靠“你是专家”就能稳定输出  
  修正：必须明确任务、边界和输出格式。

- 误区：一次调通就结束  
  修正：提示工程是持续迭代过程，必须做评测回归。

- 误区：把业务规则全写提示词  
  修正：强约束逻辑应由程序实现（校验、过滤、权限）。

- 误区：忽略失败样本  
  修正：失败样本是最有价值的优化数据。

---

## 9. 安全与合规要点

- 防 Prompt Injection：系统规则与用户输入隔离；
- 工具调用白名单：仅允许必要工具，参数严格校验；
- 数据最小暴露：上下文与日志避免敏感明文；
- 高风险领域（医疗/法律/金融）增加人工复核与免责声明；
- 审计留痕：保留请求 ID、模型版本、决策路径。

- [ ] 定义结构化输出 schema  
- [ ] 写出系统边界与拒答策略  
- [ ] 准备最小 few-shot 示例（可选）  
- [ ] 建立评测集并跑基线  
- [ ] 版本化提示词并记录实验结果  
- [ ] 上线后持续回收失败样本并迭代

---

## 11. 一句话结论

优秀提示工程 = 清晰任务定义 + 可执行约束 + 结构化输出 + 持续评测迭代。  
它是工程体系，不是一次性的“提示词灵感”。
