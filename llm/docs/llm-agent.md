# 纯 LLM、工具调用（Tool Calling）与 Agent 对比

本文在工程视角下对比三层常见形态：**只调 LLM**、**带工具调用的 LLM**、**Agent 系统**。抽象层级从低到高，**不是互斥标签**——高层会包含低层能力。理解差异有助于少写无效循环、少踩安全与可观测性坑。

---

## 0. 三层总览（先记这一张表）

| 维度 | 纯 LLM（无工具 / 无外部作用域） | 工具调用（Tool Calling） | Agent |
| --- | --- | --- | --- |
| **是什么** | 仅 **文本 in / 文本 out**（或同类多模态），不通过框架去调**你的**函数/HTTP/DB；知识来自**训练、系统提示、你塞进上下文的文字** | 模型按 schema **声明**要调用的工具与参数；**运行时代码**真正执行，再把**工具结果**回灌模型；步数常**有上限或由你写死** | 为完成**开放目标**，在「模型 ↔ 工具」外再包 **决策循环或状态图**：何时继续、何时分支、何时停、记忆与人在回路等 |
| **能否接触「当前真实世界」** | **否**（除非你已在 prompt 里粘贴了实时数据） | **能**（经你实现的工具：查库、搜 API、跑代码等） | **能**，且可**多步组合**多种工具与策略 |
| **典型失败** | **幻觉、过时知识、算术/逻辑长链不稳** | 工具选错、参数错、**单次**越权或注入 | 多步**放大**错误、死循环、成本失控、难复现 |
| **成本与延迟** | **最低**（往往一次或少量模型调用） | **中**（模型 + 工具 IO，步数可控） | **高**（步数 × 模型 + 工具，波动大） |
| **工程复杂度** | **最低** | **中**（schema、鉴权、错误码回传） | **最高**（状态、观测、终止条件、安全策略） |

一句话分层：**纯 LLM 只有「嘴与脑（在上下文内）」；工具调用给 LLM 接上「手」；Agent 决定「用这双手按什么剧本、办多大事」。**

---

## 1. 概念边界（工具调用 vs Agent，细读）

| 维度 | 工具调用（Tool Calling） | Agent |
| --- | --- | --- |
| **是什么** | 模型在**单条（或有限步）**响应里，按约定格式声明「要调哪个工具、传什么参数」；由**运行时**执行工具并把结果**再喂给模型**（可重复多轮，但**编排逻辑**在框架/业务代码里） | 在工具调用之上，再包一层**目标驱动**的**循环或图**：多步推理、重试、分支、记忆、人在回路等，**谁决定「何时停、下一步做什么」**由 Agent 策略定义 |
| **典型问题** | 「这个查询该走哪个 API？参数怎么填？」 | 「为完成用户目标，**需要哪些步骤、顺序、失败怎么办？**」 |
| **控制流在谁手里** | 常是 **if/else + 一次或固定次数** 的「模型 → 工具 → 模型」管线；或 **ReAct/函数调用** 的**显式协议** | 在 **Agent 框架/图（如 LangGraph）** 或**手写状态机**里；可含**规划、子 Agent、条件边** |
| **是否等于 Agent** | **不是**。仅有工具能力时，只是「可调外部能力的模型」 | **是**一种**系统模式**：模型 + 工具 + **决策循环** +（通常）**状态** |

---

## 1.1 纯 LLM 单独补充（与工具/Agent 的差异源）

- **知识边界**：受训练数据截止、静态提示影响；**不会自动**知道「此刻股价、本库最新订单」除非你先检索再塞上下文（那种「检索再生成」若不经工具协议，仍属你在应用层编排，模型本身仍是纯推理）。
- **事实与计算**：长链路算术、条文引用、表格运算更易出错；需要事实时常用 **RAG（检索增强）** 或 **工具** 补足，而不是再多堆一层「更大模型」。
- **何时坚持纯 LLM 就够**：文案改写、头脑风暴、代码片段解释、**不要求实时外部状态**且合规允许「可能不准」的场景。

与后两者的关系：**纯 LLM ⊂ 能力基底**；一旦引入「模型发起的、由代码执行的外部动作」，就进入**工具调用**层；再叠加**目标驱动的多步编排**，进入 **Agent** 层。

---

## 2. 关系：层层包含，而非三者互斥

- **纯 LLM**：任何 Agent / 工具链路里，**最后一步往往是 LLM 生成**；没有工具时整条系统也可以「只有 LLM」。
- **纯聊天 / 无工具**：没有工具调用，也谈不上典型 Agent（除非把「多轮对话」泛称 agentic，但**无外部作用域**）。
- **带工具、但只跑固定步数**（例如：最多 1 次 `model → tool → model`）：这是 **工具调用管线**，常**不**称为完整 Agent。
- **ReAct / 函数调用多轮直到终止条件**：**Tool-using Agent** —— **工具调用是子机制**，**循环与终止条件**才是 Agent 层。

对比表应读作：**Agent ⊃ 工具调用 ⊃ 纯 LLM 作为推理核**（常见形态）；**不是**「LLM vs Agent」二选一，而是**在同一任务里选哪一层够用**。

---

## 3. 能力对比（细项）

### 3.0 纯 LLM（相对后两者的短板）

- **无内置「真实世界接口」**：不能替你执行查询、改库、下单；最多只在上下文里「编造看似合理的结构化输出」。
- **规划与步数**：单次生成可很长，但**没有**框架意义上的「第几步工具」；多轮对话仍是「多条纯文本」，除非外挂检索/工具。
- **其余维度**：成本最低、观测最简单（单次请求日志）；安全风险主要是提示注入与输出合规，**无工具链式副作用**。

以下 **3.1～3.6** 仍聚焦 **工具调用 vs Agent**（在已接入外部能力的前提下）。

### 3.1 规划与步数

- **工具调用**：单轮可返回多个 tool call；多轮由**你写的循环**或**模型一次输出**决定，**没有**统一标准叫「几阶 Agent」。
- **Agent**：显式处理 **max_iterations**、预算 token、**DAG / 状态图**，避免死循环或失控调用。

### 3.2 状态与记忆

- **工具调用**：状态往往是「当前请求上下文」；历史要靠你自己塞进 prompt 或 session。
- **Agent**：常绑定 **thread/session、checkpoint、长期记忆**（向量库/摘要/图谱等），**状态**是的一等公民（尤其 LangGraph 等）。

### 3.3 可观测与审计

- **工具调用**：日志主要是「请求 / 某次 tool 入参出参 / 再请求」；步数少时够用的。
- **Agent**：需要 **Trace、每步 tool 与模型边、重试与分支**；与 LangSmith 等 **span 级** 观测更匹配。

### 3.4 安全与权限

- **工具调用**：风险集中在**单次**参数注入、越权 API；面相对小。
- **Agent**：**多步放大**误用（链式写库、多次搜索泄露）；需 **工具白名单、确认门、只读/沙箱、每步鉴权**。

### 3.5 成本与延迟

- **工具调用**：通常 **1～3 次** 模型调用即可结束，成本可预期。
- **Agent**：**步数 × 每步模型 + 工具 IO**，波动大；需限流、缓存、**子目标尽早出口**（不要为「像 Agent」而硬绕远路）。

### 3.6 调试难度

- **工具调用**：prompt / schema / 工具实现三步定位。
- **Agent**：还要查 **为何选这一步工具、为何不重试、为何提前结束**，更难复现。

## 4. 选型建议（可执行）

### 4.0 优先「纯 LLM」（连工具都不要上）

- 输出**不依赖**实时数据、私有库、精确计算或可执行副作用。
- 延迟与成本**极致敏感**，且团队暂时不想维护工具安全与 schema。
- 接受「可能幻觉」或与事实类产品已有 **人工审核**。

### 4.1 再上「工具调用管线」（不做完整 Agent）

- 任务可分解为 **单次检索 / 单次 SQL / 单次 HTTP**，且顺序固定。
- 产品能接受 **固定上限**（例如最多两轮模型）。
- 要强可控、低延迟、低成本。

### 4.2 再上 Agent

- 用户目标是 **开放式**（「调研某主题并给报告」「修这个仓库里的 bug」）。
- 需要 **分支**（if 查询为空则换策略）、**失败重试**、**人机确认**。
- 需要 **跨多工具** 且顺序**无法事先写死**。

### 4.3 反模式

- **能用纯 prompt 解决且无所谓事实新鲜的**，不要强行接工具或 Agent。
- **能用「一次 tool + 一次回答」解决的，不要上多轮 Agent**：延迟、费用、调试成本都会上去。
- **把「Agent」当营销词**：内部仍是单次 function calling，徒增认知负担。

---

## 5. 与常见框架的对应（便于对照文档）

- **纯 LLM**：各厂商 **Chat Completions / Responses**；LangChain 里 **`ChatModel.invoke`**、**LCEL** `prompt | llm | parser`，无 `bind_tools`。
- **仅 Tool Calling**：OpenAI / Anthropic 等 **functions / tools API**；LangChain「**绑工具的 ChatModel + 手写一轮或两轮」**。
- **Agent**：LangChain **`create_agent`**、**LangGraph** 状态图、**deepagents** 等「带循环与中间策略」的封装；或自写 **while + 终止条件**。

---

## 6. 小结

|  | 纯 LLM | 工具调用 | Agent |
| --- | --- | --- | --- |
| **核心** | 仅上下文内推理与生成 | 模型**声明**外部动作，运行时**执行**并回灌 | **多步决策 + 工具 +（通常）状态** |
| **典型代码形态** | `prompt \| llm \| parser` | `bind_tools` → `invoke` → 执行 tool → 再 `invoke`（可选） | 同上 + **循环/图/规划** 与 **终止条件** |
| **何时选** | 无需外部事实/副作用、要极省 | 路径短、步数可控、要省钱省时 | 路径长、要容错、要强编排 |

**纯 LLM 是推理核；工具调用给模型接外部世界；Agent 是在约束下把多步办成事的体系。** 常规路线：**先纯 LLM 试边界 → 缺事实再接 RAG/工具 → 步骤与分支复杂再上 Agent**，迭代成本通常最低。
